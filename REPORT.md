# Design Report

## Architecture

The system is a focused TypeScript vertical slice with five boundaries. A local Express application provides a synthetic servicing workflow with server-rendered pages, tables, an iframe, redirects, and injected runtime conditions. Discovery uses the OpenAI Responses API with `gpt-5.6-terra`: on each turn it sends an in-memory screenshot plus a compact accessibility and visible-text observation, accepts exactly one strict `propose_action` function call, validates the proposal, applies policy, and executes it through Playwright. The persisted discovery log contains redacted observations, model response IDs, token usage, policy decisions, target resolutions, results, and independent completion verification; screenshot bytes are not persisted.

A compiler separates observed mechanics from reviewed product meaning. It takes the genuine successful discovery log plus a reviewed compilation profile. The trace supplies the actions and targets that actually executed; the profile supplies the capability contract, stable step IDs, risk labels, checkpoints, typed outputs, business outcomes, and runtime conditions. The compiler rejects failed or unverified discovery, missing policy or target evidence, redaction markers, and discovery-time sensitive literals. It emits a JSON capability with provenance back to the exact source log.

Replay loads that artifact and invokes Playwright directly. It has no dependency on the discovery decision source and makes no OpenAI call. A shared policy module guards discovery, replay, browser requests, and navigation during operator control. A `SurfaceAdapter` isolates artifact semantics from Playwright handles. A `SessionControl` plus handoff coordinator owns the automation → paused → human → automation state transitions. JSONL evidence is written at the execution boundary and redacted before persistence. This stays in one process deliberately: queues, databases, remote browsers, and a service mesh would add deployment work without strengthening the core decisions this assignment evaluates.

## Artifact schema

The versioned artifact is a reviewable capability contract rather than a model transcript. It declares identity and semantic version, purpose, application family and compatible version, typed inputs and outputs, ordered steps, success criteria, expected business outcomes, runtime conditions, and discovery provenance. Inputs are referenced by name (`inputRef: "member_id"`), so the discovery member ID never becomes a saved action literal. Outputs declare their type and parser; the balance output is USD money with a fixed `{ amount, currency }` shape.

Each step has a stable ID, description, risk class, action, target, and optional postcondition. Targets use ranked semantic candidates: accessible role and name, label, exact visible text with optional context, or a table value paired with a row header. A titled-frame scope handles the legacy-style balance iframe. Replay accepts exactly one match, tries a later candidate only after no match, and stops on ambiguity. Coordinates and arbitrary CSS or XPath are excluded from schema version 1 because they are difficult to review and too easy to apply to the wrong control.

Runtime behavior is also data. The artifact declares the no-match business outcome and four runtime conditions: bounded slow-load recovery, permission denial, session expiry with screenshot evidence, and an unexpected dialog requiring intervention. Provenance stores the discovery session, provider, model, compilation time, and SHA-256 of the exact discovery log. The compiler/profile boundary is a deliberate trade-off: it preserves what the model actually did while requiring a human-reviewed statement of product semantics instead of asking the model to infer a reusable API contract from arbitrary page text.

## Determinism & error handling

Replay validates invocation inputs before opening Chrome, substitutes named values, resolves every target uniquely, applies the same action policy used during discovery, executes steps in artifact order, checks reviewed postconditions, parses declared outputs, verifies final success, and checks required application markers. Evidence records `decisionSource: "artifact"` and `modelCalls: 0`. Timestamps and session IDs vary; action choice, retry budgets, checkpoints, and result classification do not.

The result taxonomy separates success, expected business outcomes, failures, and intervention. Invalid input returns `INVALID_MEMBER_ID` before browser launch. A valid unknown ID returns `MEMBER_NOT_FOUND`, not a crash. Slow loading is the only automatic recovery: exact reviewed loading text triggers one wait-until-absent attempt capped at five seconds. Permission denial and session expiry stop immediately as runtime failures. An unknown missing or ambiguous target becomes possible drift rather than a guessed click. Policy violations and other execution errors remain distinct categories. Failures include capability, step, code, category, expected state, observed state, and evidence reference.

The mock app injects each condition through a session-scoped `/start?scenario=...` query; replay still performs the full task through the UI. Real-Chrome tests cover the normal path, validation, not found, recovery, hard failures, intervention, abort, timeout, unresolved intervention, and altered-target drift. The evidence audit verifies artifact hashes, terminal results, redaction, and zero model calls. No bounded LLM fallback was added: an uncertain replay stops or hands control to a person instead of silently becoming nondeterministic.

## Heterogeneity & multi-tenant

The artifact contains surface-level intent while `SurfaceAdapter` owns observation, target resolution, action, reading, and failure capture. The current adapter uses Playwright and accessibility-first locators, but the contract does not expose DOM nodes or Playwright locator strings. A desktop adapter could map the same role/name and text candidates to OS accessibility elements and implement click, fill, read, and observation with a desktop automation framework. A more hostile legacy-web adapter could add reviewed visual anchors or coordinates as a new versioned target variant. The iframe and table-value target already exercise two common legacy patterns.

Compatibility is selected by application family and version markers, not by one institution's URL. The intended production model is a reviewed base capability per vendor family, plus narrowly scoped tenant/version overrides for branding, labels, entry routing, or target candidates. The schema has a tenant override identifier seam, while required markers and target/checkpoint failures expose incompatibility. Overrides would be separately versioned, tested against their tenant fingerprint, and promoted only after successful replay. This project does not implement an override registry or a second tenant; those remain design work rather than a claimed demonstration.

## Escalation & handoff

Discovery can request a human, and replay can detect a declared intervention condition. The demonstrated case is an unexpected Account Notice after the savings link is opened. Noninteractive mode returns `intervention_required`. Interactive mode keeps the same browser context and page alive, displays context in the terminal, and waits for a named operator to type `take`. Ownership moves from automation to paused to human, and automation gates reject actions while it lacks control.

The operator acts in visible Chrome. Native click instrumentation and navigation-request auditing record safe action identity without form values. Typing `resume` returns ownership to automation; the runner rechecks URL policy and verifies that the blocking condition disappeared before it completes the interrupted step checkpoint. It then continues to the balance read without repeating the original click. Abort, timeout, unresolved state, and invalid handoff sequences return explicit intervention failure codes. Request routing remains active while the person controls Chrome: the dismissal route is allowed, while account-closing routes remain denied and are logged if attempted.

Both an automated integration run and a genuine manual run prove automation → paused → human → automation → finished in one session. The manual evidence identifies the operator, records the native dismissal POST, revalidates successfully, continues deterministic replay, and finishes with zero model calls.

## Safety

An explicit JSON policy allowlists origin, anchored route patterns, and action types. The central action gate checks current and destination URLs, resolved control identity, declared risk, and session ownership. Browser request routing applies the route policy to redirects, frames, popups, automated actions, and operator navigation. Close Account and Confirm Close Account are human-required controls, and all close-account routes are denied. The mock application's own confirmation screen is not treated as the safety boundary.

Secrets remain in environment variables; `.env` is ignored. Artifact compilation rejects known sensitive literals. Evidence redaction recursively masks configured invocation values, secret-named fields, member IDs embedded in URLs or snapshots, account numbers, and money values. Model screenshots are sent in memory and not written to logs. Replay evidence excludes provider/model metadata and proves zero model calls. Failure screenshots are opt-in per reviewed runtime condition; the committed session-expiry screenshot was visually inspected and contains no member or account details.

The limits are explicit. This uses invented local data, not a real financial system. Production deployment would require authenticated operator identity, encrypted evidence storage, retention rules, tenant isolation, authorization beyond a local JSON file, screenshot redaction or suppression for arbitrary screens, signed artifact approval, and tamper-evident audit storage.

## Cuts

I chose one complete capability and deep runtime coverage over breadth. The implementation does not include a native desktop adapter, visual-coordinate fallback, remote co-browsing console, distributed job system, persistent artifact registry, tenant override service, or a real bank integration. The terminal plus visible Chrome is the minimal real operator surface. The compatibility and surface seams are implemented, while desktop and multi-tenant behavior are documented rather than simulated as finished features.

No optional stretch goal is claimed. There is no agent-facing capability catalog, generated test code, confidence/approval lifecycle, LLM-assisted replay repair, second-tenant demonstration, or multi-run flakiness score. Input parameterization and vendor-family metadata support future reuse but are part of the core capability contract here. With more time, I would first add signed draft/approved artifact promotion with repeated replay reliability metrics, then a small capability catalog API. After that I would add reviewed tenant overrides and one desktop adapter. A bounded LLM fallback would come later because it increases both safety and evidence complexity.
